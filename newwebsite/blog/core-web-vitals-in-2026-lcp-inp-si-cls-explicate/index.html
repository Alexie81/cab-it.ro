Core Web Vitals în 2026: LCP, INP și CLS explicate

Core Web Vitals măsoară încărcarea principală, răspunsul la interacțiuni și stabilitatea vizuală, folosind evaluarea la percentila 75 pentru datele de teren.

Publicat la 19.08.2026 · actualizat la 19.08.2026 · scris și revizuit de Alexie Popescu

O decizie legată de Core Web Vitals în 2026 trebuie să conecteze publicul, oferta, implementarea și rezultatul comercial. Țintește LCP de cel mult 2,5 secunde, INP de cel mult 200 ms și CLS de cel mult 0,1 pentru cel puțin 75% dintre vizite, pe mobil și desktop. Obiectivul acestui ghid este să transforme termenul într-un proces clar, adaptabil unei firme mici sau medii din România.

Răspuns rapid

Criteriul de decizie: Începe cu datele reale din Search Console sau CrUX, identifică template-urile afectate și optimizează cauza dominantă, nu doar scorul unui test izolat. Evaluează întotdeauna oferta, publicul, resursele, pagina folosită și traseul solicitării până la vânzare.

LCP: conținutul principal

Largest Contentful Paint urmărește momentul în care cel mai mare element relevant din viewport este redat. Imaginile hero, fonturile, serverul și resursele blocante sunt cauze frecvente. Pentru implementare, urmărește în mod explicit:

  • TTFB
  • hero image
  • preload
  • critical CSS

Optimizează lanțul complet până la element, nu doar dimensiunea fișierului.

INP: răspunsul la interacțiuni

Interaction to Next Paint evaluează latența interacțiunilor pe durata vizitei. JavaScriptul lung, randarea și handler-ele pot întârzia feedbackul. Pentru implementare, urmărește în mod explicit:

  • long tasks
  • event handlers
  • main thread
  • rendering

Un site poate încărca rapid și totuși să răspundă greu la click sau tastare.

CLS: stabilitatea vizuală

Cumulative Layout Shift crește când elementele se mută neașteptat. Dimensiunile lipsă, bannerele și fonturile pot deplasa textul sau butoanele. Pentru implementare, urmărește în mod explicit:

  • width/height
  • reserved space
  • font fallback
  • dynamic content

Rezervă spațiul înainte ca elementele să apară și evită inserțiile deasupra conținutului.

Field data vs lab data

Datele CrUX reflectă utilizatori reali pe o fereastră, iar Lighthouse simulează un scenariu și ajută diagnosticul. Ele pot diferi fără ca unul să fie greșit. Pentru implementare, urmărește în mod explicit:

  • Search Console CWV
  • CrUX
  • PageSpeed lab
  • device și rețea

Folosește terenul pentru evaluare și laboratorul pentru depanare.

Prioritizează pe template

Grupează paginile după homepage, serviciu, articol, categorie și produs. Repararea unei componente comune poate îmbunătăți sute de URL-uri. Pentru implementare, urmărește în mod explicit:

  • template
  • componentă comună
  • monitorizare release
  • regresie

Include bugete de performanță și testare în procesul de dezvoltare.

Cum măsori rezultatele

Leagă datele platformei de rezultatul comercial. Clickul, apelul sau formularul sunt etape; verifică relevanța, calificarea, oferta și vânzarea înainte de a muta bugetul. Pentru subiectul Core Web Vitals în 2026, păstrează o definiție stabilă a succesului și compară perioade sau segmente comparabile.

  • cost pe lead calificat
  • rată de conversie a paginii
  • rată lead–client
  • valoare de conversie și profitabilitate

Automatizarea devine mai bună doar când primește semnale curate și suficient feedback despre ce înseamnă un client valoros. Documentează sursa datelor, intervalul și orice schimbare majoră de ofertă, buget sau implementare.

Exemplu practic

Un website are LCP slab pe toate paginile de serviciu deoarece folosește aceeași imagine hero mare și un script care întârzie randarea. Echipa optimizează componenta comună, comprimă imaginea, stabilește dimensiunile și mută JavaScriptul necritic, apoi urmărește datele de teren după suficient timp. Scenariul este orientativ și ilustrează logica de decizie; costurile, ritmul și rezultatele reale trebuie stabilite din datele fiecărei afaceri.

Greșeli frecvente

  • optimizarea doar a homepage-ului
  • confundarea scorului Lighthouse cu datele reale
  • eliminarea funcțiilor fără analiză
  • ignorarea regresiilor
  • schimbări fără monitorizare

Plan de acțiune

  1. verifică field data
  2. grupează template-urile
  3. identifică elementul sau taskul
  4. optimizează cauza
  5. monitorizează după release

Întrebări frecvente

Care sunt pragurile bune?

LCP ≤ 2,5 s, INP ≤ 200 ms și CLS ≤ 0,1, evaluate la percentila 75, conform documentației actuale.

Un scor 100 garantează ranking?

Nu. Performanța este doar o parte din sistemele de ranking și experiență; relevanța și conținutul rămân esențiale.

De ce PageSpeed diferă între teste?

Rețeaua, serverul, cache-ul și simularea variază. Analizează tendințe și date de teren, nu o singură rulare.
